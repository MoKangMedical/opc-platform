# 多Agent协作编排体系

> **导语**：一个Agent是"得力助手"，多个Agent协同工作是"一支军队"。当你从"让AI帮忙做一件事"进化到"让AI系统性地运营整个业务"，你就进入了多Agent编排的领域。这不是技术的炫耀——它是OPC创业者从"月收入1万"到"月收入10万"的核心杠杆。因为你不再是一个人+AI，而是一个人指挥一支AI军团，每个子Agent各司其职、并行推进。本课程将带你深入Hermes Agent的多Agent编排体系，从原理到实战，构建你的"AI军团"。

---

## 一、为什么需要多Agent：从单兵到军团

### 1.1 单Agent的"能力天花板"

一个Agent再强，也有三个不可逾越的限制：

**限制一：上下文窗口瓶颈**
每个大模型都有上下文窗口上限（如128K tokens）。当你试图让一个Agent同时处理"写代码+做市场调研+回复客户邮件+管理项目进度"时，它的上下文窗口会被各种任务的中间结果撑爆。表现就是：Agent开始"遗忘"早期的任务、回答质量下降、甚至完全跑偏。

**限制二：认知切换成本**
人类在不同任务间切换需要"热身时间"，AI也有类似问题。一个Agent在"写代码"模式下表现优秀的prompt风格，可能完全不适用于"写营销文案"。让一个Agent身兼数职，等于让它不停地在不同的"认知模式"间切换，每种都做不到极致。

**限制三：单线程执行**
单个Agent本质上是一个顺序执行者——它一次只能做一件事。如果说一个Agent 1天能完成10个单位的工作量，10个Agent理论上是100个单位。顺序执行的效率天花板就是你的时间。

### 1.2 多Agent的"分而治之"哲学

多Agent系统的核心思想是：**把一个复杂任务拆分成多个子任务，每个子任务由专门的Agent负责，它们之间通过协作完成整体目标。**

类比理解：
- **单Agent** = 一个全栈工程师，什么都能干，但一天只能干一个人的活
- **多Agent系统** = 一个虚拟公司，有前端、后端、测试、设计、运营——各自专注，并行推进

**多Agent不是"把一个人拆成多个"，而是"用组织的方式放大个体"。**

### 1.3 多Agent适用的OPC场景

以下场景，单Agent开始吃力，多Agent开始发光：

| 场景 | 单Agent的困境 | 多Agent方案 |
|------|-------------|-----------|
| **产品开发+市场推广同步进行** | 上下文混在一起，代码里夹着营销文案 | 开发Agent + 内容Agent，各司其职 |
| **多客户并行服务** | 不同客户的需求在同一个对话里互相污染 | 每个客户一个独立Agent |
| **长周期研究项目** | 对话历史越来越长，质量逐渐下降 | Research Agent → 报告写给决策Agent |
| **复杂工作流** | 步骤多到Agent自己都记不住 | 编排Agent管理流程，执行Agent各自干活 |

### 1.4 多Agent系统的核心挑战

承认挑战，才能应对挑战：

- **通信成本**：Agent之间如何高效传递信息？传得太多浪费Token，传得太少信息不足
- **状态一致性**：多个Agent同时操作同一个文件/数据库怎么办？
- **错误传播**：上游Agent的一个小错误，到下游可能被放大10倍
- **成本控制**：多个Agent = 多个API调用 = 更高的费用。如何平衡效果与成本？

这些问题，我们会在后续小节逐一拆解。

## 二、delegate_task深度剖析

### 2.1 delegate_task是什么？

`delegate_task` 是Hermes Agent实现多Agent协作的核心原语。它的作用非常简单：**让当前Agent（编排者）创建一个子Agent（执行者），给它一个独立的任务和上下文，让它独立完成，然后把结果返回给编排者。**

```python
# 概念示例（非实际API）
result = delegate_task(
    task="分析这个CSV文件中的销售数据，找出Top 5产品和季节性趋势",
    context={
        "file_path": "/data/sales_2024.csv",
        "focus": "产品分析和趋势"
    },
    agent_role="数据分析专家",
    model="claude-sonnet-4-20250514"  # 可以用不同模型
)
```

### 2.2 delegate_task的工作原理

当你调用 `delegate_task` 时，底层发生了什么：

```
步骤1：编排Agent将任务描述+上下文打包
  ↓
步骤2：创建一个新的Agent实例（独立上下文窗口）
  ↓
步骤3：子Agent加载任务+相关Skills
  ↓
步骤4：子Agent独立执行（可以调用工具、搜索、读写文件）
  ↓
步骤5：子Agent完成任务，将结果打包返回
  ↓
步骤6：编排Agent接收结果，决定下一步（合并/验证/重新分配）
```

**关键特性：子Agent拥有独立的上下文窗口。**这意味着子Agent的"记忆"不会污染编排Agent的"记忆"，反之亦然。这是解决"上下文窗口瓶颈"的核心机制。

### 2.3 delegate_task的调用策略

**策略一：同步委托（等结果再继续）**

适用于：子任务之间有依赖关系。

```
编排：Agent A → 委托给 子Agent B → 等待B返回 → 基于B的结果委托给 子Agent C
```

**策略二：异步委托（同时发出多个任务）**

适用于：子任务之间相互独立。

```
编排：Agent A ─→ 委托给 子Agent B（任务1）
              ─→ 委托给 子Agent C（任务2）
              ─→ 委托给 子Agent D（任务3）
              ↓ 三个任务并行执行
              ↓ 全部完成后，汇总结果
```

**策略三：流水线委托（链式处理）**

适用于：数据需要多阶段加工。

```
原始数据 → Agent A（清洗） → Agent B（分析） → Agent C（可视化） → Agent D（报告）
```

### 2.4 选择合适的模型给子Agent

不同子Agent用不同模型——这是多Agent系统的一大优势：

| 子Agent角色 | 推荐模型 | 原因 |
|------------|---------|------|
| 代码生成 | Claude Sonnet / DeepSeek Coder | 代码能力最强 |
| 数据分析 | GPT-4o / Claude Sonnet | 数理逻辑强 |
| 内容写作 | Claude Opus / GPT-4o | 文笔最好 |
| 简单查询 | GPT-4o mini / DeepSeek V3 | 成本低，速度快 |
| 文件操作 | GPT-4o mini | 不涉及复杂推理，可以用便宜模型 |
| 编排决策 | Claude Sonnet / GPT-4o | 需要强推理和指令遵循能力 |

**省钱技巧**：不是所有子Agent都需要用最贵最强的模型。识别出"关键路径上的Agent"（用强模型）和"辅助性的Agent"（用便宜模型），可以节省50%以上的API费用。

## 三、子代理设计模式：Leaf vs Orchestrator

### 3.1 两种基本角色：Leaf和Orchestrator

在多Agent系统中，Agent扮演两种基本角色：

**Leaf（叶子节点）**：
- 只执行具体任务，不委托其他Agent
- 输入：任务描述+数据 → 输出：完成的结果
- 类比：生产线上的一个工位
- 特点：简单、可靠、易于调试

**Orchestrator（编排节点）**：
- 不执行具体任务，只负责分解任务、委托Leaf、汇总结果
- 输入：复杂目标 → 输出：协调后的最终成果
- 类比：项目经理/指挥
- 特点：需要强推理能力，但不直接操作数据

### 3.2 设计模式一：星型结构（一个Orchestrator + 多个Leaf）

最基础也最实用的多Agent模式：

```
              ┌─────────────┐
              │ Orchestrator │ ← 你直接对话的Agent（项目总管）
              └──┬──┬──┬───┘
                 │  │  │
     ┌───────────┘  │  └──────────┐
     ▼              ▼              ▼
┌─────────┐  ┌─────────┐  ┌─────────┐
│ Leaf A  │  │ Leaf B  │  │ Leaf C  │
│ 写代码   │  │ 写文档   │  │ 做测试   │
└─────────┘  └─────────┘  └─────────┘
```

**适用场景**：任务可以分解为多个独立子任务。

**OPC案例**：开发一个新功能。
- Orchestrator：理解需求 → 拆分为子任务 → 分配 → 验收 → 汇总
- Leaf A：写后端API代码
- Leaf B：写前端组件代码
- Leaf C：写单元测试
- 三个Leaf并行工作，完成后由Orchestrator整合

### 3.3 设计模式二：树型结构（层级编排）

当任务足够复杂时，引入层级：

```
              ┌──────────────┐
              │ 总Orchestrator │ ← 项目总指挥
              └──┬────────┬──┘
                 │        │
    ┌────────────┘        └────────────┐
    ▼                                  ▼
┌─────────────┐                ┌─────────────┐
│ Orchestrator │                │ Orchestrator │
│  后端组主管   │                │  前端组主管   │
└──┬──────┬───┘                └──┬──────┬───┘
   │      │                      │      │
   ▼      ▼                      ▼      ▼
┌────┐ ┌────┐              ┌────┐ ┌────┐
│Leaf│ │Leaf│              │Leaf│ │Leaf│
│API │ │DB  │              │UI  │ │状态│
└────┘ └────┘              └────┘ └────┘
```

**适用场景**：大型项目，子任务之间有明显分组。

**层级深度的建议**：大多数OPC场景，2层（总Orchestrator → Leaf）就够了。超过3层会导致信息传递失真，得不偿失。

### 3.4 设计模式三：点对点协作（Agent之间直接通信）

不需要中心化的Orchestrator，Agent之间直接对话：

```
┌──────────┐    直接通信    ┌──────────┐
│ Agent A  │ ←───────────→ │ Agent B  │
│ 研究员    │               │ 写作者    │
└──────────┘               └──────────┘
      │                        │
      │     ┌──────────┐       │
      └───→ │ Agent C  │ ←────┘
            │ 审核员    │
            └──────────┘
```

**适用场景**：Agent之间有持续的交互需求，比如"研究员持续为写作者提供素材"。

**注意事项**：点对点模式容易产生"通信混乱"——如果5个Agent两两通信，就是10条通信链路。保持Agent数量在3个以内。

### 3.5 如何选择设计模式：决策树

```
你的任务能分成独立的子任务吗？
  ├── 是 → 子任务之间有依赖关系吗？
  │         ├── 没有 → 用星型结构（最推荐）
  │         └── 有 → 用流水线模式（Leaf按顺序执行）
  └── 否 → 任务需要持续的多方协作吗？
            ├── 是 → 用点对点协作
            └── 否 → 你不需要多Agent，单Agent就够了
```

**最重要的一条建议**：不要为了用多Agent而用多Agent。如果一个Agent能做好，就别引入复杂性。多Agent是解决"单Agent做不好"的问题，不是解决"看起来很酷"的需求。

## 四、并行工作流设计：如何同时推进多个任务

### 4.1 并行化的前提条件

不是所有任务都能并行。判断标准：**子任务之间没有数据依赖就可以并行。**

```python
# ✅ 可以并行：三个独立任务
任务A：分析用户反馈数据.csv
任务B：竞品官网截图分析
任务C：写本周周报草稿

# ❌ 不能完全并行：有依赖关系
任务A：写PRD → 任务B：根据PRD写代码 → 任务C：测试代码
# 解决方案：流水线而非并行
```

### 4.2 并行执行的技术实现

Hermes Agent中，并行委托多个子Agent：

```
你 → Orchestrator: "我需要你同时做三件事：分析上周销售数据、检查网站SEO问题、起草下个月的营销计划"

Orchestrator:
  ├─→ delegate_task(销售分析) ──→ 子Agent A 开始工作
  ├─→ delegate_task(SEO检查)  ──→ 子Agent B 开始工作  
  └─→ delegate_task(营销计划) ──→ 子Agent C 开始工作
  
  [三个Agent同时工作...]

  子Agent A 完成 → 返回销售分析报告
  子Agent B 完成 → 返回SEO问题清单
  子Agent C 完成 → 返回营销计划草案

Orchestrator 汇总 → 生成综合报告给你
```

**实际耗时**：假设每个任务单独需要10分钟。串行=30分钟，并行≈10分钟（取最慢的那个）。效率提升3倍。

### 4.3 并行工作流中的资源竞争

当多个Agent同时操作同一个文件或数据库时，会出现"竞争条件"：

**问题场景**：Agent A 和 Agent B 同时修改 `config.json`。

**解决方案：**

1. **分区策略**：提前划分好"领地"
   ```
   Agent A 只能动 /project/backend/
   Agent B 只能动 /project/frontend/
   共享配置由Orchestrator统一管理
   ```

2. **乐观锁**：Agent修改文件前检查"上次修改时间"，如果发现被改了则重新读取

3. **写入代理**：所有写操作通过Orchestrator中转，Orchestrator负责排队

**最简单的实践**：作为OPC创业者，你不用自己实现复杂的并发控制。只需要在设计工作流时，**让并行的Agent操作不同的文件/目录**，就能避免99%的资源竞争问题。

### 4.4 并行工作流设计模板

**模板一：研究-创作-发布 三线并行**

```
你：写一篇关于"AI对独立开发者影响"的深度文章

Orchestrator分解：
  线1（研究）：搜索最新数据+找3个案例 → 5分钟
  线2（初稿）：写大纲+填充内容 → 10分钟  
  线3（素材）：生成封面图+信息图 → 5分钟

三条线并行推进 → 15分钟内全部完成 → Orchestrator整合
```

**模板二：多客户并行服务**

```
你：今天需要回复3个客户的咨询

Orchestrator：
  Agent A：处理客户A的咨询（查看历史→分析需求→起草回复）
  Agent B：处理客户B的咨询
  Agent C：处理客户C的咨询

全部完成后→ Orchestrator汇总 → 你逐一确认后发送
```

## 五、Agent间通信与状态管理

### 5.1 通信模式：Shared File System

Hermes Agent的多Agent通信主要通过**共享文件系统**实现。这是最简单也最可靠的Agent间通信方式：

```
Agent A 完成工作 → 将结果写入 /workspace/output/task_a_result.md
Agent B 读取 → /workspace/output/task_a_result.md → 继续处理
```

**为什么用文件而不是内存？**
- **持久化**：文件不会因为Agent重启而丢失
- **可审计**：你可以随时查看中间结果
- **解耦**：Agent A不需要知道Agent B的存在
- **标准化**：Markdown/JSON格式，所有Agent都能读

### 5.2 结构化输出约定

为了让Agent之间的信息传递更丝滑，建议约定标准输出格式：

```json
// Agent的标准输出格式
{
  "agent_id": "data-analyst-001",
  "task_id": "sales-analysis-2024q1",
  "status": "completed",  // completed | failed | needs_clarification
  "summary": "2024 Q1销售额同比增长23%，Top产品为...",
  "data": {
    "key_findings": [...],
    "charts": [...],
    "raw_data_path": "/output/sales_q1_clean.csv"
  },
  "errors": [],
  "next_steps": ["建议将本结果传递给 marketing-planner Agent"]
}
```

**关键字段说明**：
- `status`：让接收方Agent快速判断是"可以直接用"还是"需要处理异常"
- `summary`：人类可读的摘要，也方便Orchestrator快速浏览
- `data`：结构化数据，供下游Agent程序化处理
- `next_steps`：意图传递——建议下游Agent做什么

### 5.3 状态追踪：谁做了什么、做到哪了

在多Agent系统中，"搞清楚现在什么状态"是最容易被低估的挑战。

**解决方案：任务状态看板（Task Board）**

在共享目录中维护一个 `TASK_BOARD.md`：

```markdown
# 项目：AI资讯聚合平台开发

## 整体进度：60%

### 后端API开发
- [x] 数据库Schema设计 → data-architect Agent（完成）
- [x] 用户认证模块 → backend-auth Agent（完成）
- [ ] 资讯聚合接口 → backend-api Agent（进行中，预计还需要30分钟）
- [ ] 单元测试 → test-backend Agent（等待上游完成）

### 前端开发
- [x] 页面布局 → frontend-ui Agent（完成）
- [ ] 数据联调 → frontend-integration Agent（等待后端API完成）

### 部署
- [ ] CI/CD配置 → devops Agent（等待全部开发完成）
```

**Orchestrator的职责之一**：每收到一个子Agent的完成通知，就更新Task Board。这样你（人类）随时看一眼就知道全局状态。

### 5.4 上下文传递策略

子Agent需要多少上下文？这是一个需要平衡的问题：

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **全量传递** | 把所有上下文都给子Agent | 信息完整 | Token浪费，子Agent可能被无关信息干扰 |
| **最小传递** | 只给刚好够用的信息 | Token高效 | 可能漏掉关键信息 |
| **摘要传递** | 先让父Agent总结再传递 | 平衡 | 摘要可能丢失细节 |

**实践建议**：采用"分层传递"——

```
第一层（必需）：任务描述 + 输入数据 + 输出格式要求
第二层（建议）：相关背景 + 类似案例 + 注意事项
第三层（可选）：完整的项目上下文（仅在子Agent主动请求时提供）
```

## 六、故障处理与容错机制

### 6.1 多Agent系统中的故障类型

多Agent系统比单Agent更容易出问题，因为故障点更多：

| 故障类型 | 典型表现 | 影响范围 |
|---------|---------|---------|
| **子Agent超时** | 某个子Agent执行时间远超预期 | 拖慢整个工作流 |
| **子Agent崩溃** | API错误、模型拒绝回答、陷入循环 | 该子任务无法完成 |
| **结果质量差** | 子Agent返回了格式正确但内容错误的结果 | 下游Agent基于错误信息继续，错误被放大 |
| **通信断裂** | 子Agent的结果没有正确保存/传递 | 下游Agent拿到空数据或旧数据 |
| **编排错误** | Orchestrator分解任务不合理 | 整个项目的方向跑偏 |

### 6.2 超时与重试策略

**设置合理的超时时间**，并在超时后自动重试：

```
子Agent执行策略：
  第一次尝试：超时=5分钟
    └── 超时？→ 重试（可能是API波动）
  第二次尝试：超时=5分钟
    └── 超时？→ 降级处理（用更简单的模型/更小的范围）
  第三次尝试：超时=3分钟（降级版本）
    └── 超时？→ 标记为失败，通知Orchestrator走备选方案
```

**关键原则**：不要让一个子Agent的失败阻塞整个工作流。Orchestrator需要有"降级路径"——如果Agent A做不了分析报告，至少给我一个原始数据摘要。

### 6.3 结果验证机制

**不要盲目信任子Agent的输出。** 在关键节点加入验证步骤：

```python
# 概念示例
# 方案1：交叉验证
Agent A 分析数据 → 输出报告A
Agent B 分析同样的数据 → 输出报告B
Orchestrator 对比A和B → 一致则通过，不一致则深入调查

# 方案2：自检验证
Agent X 写代码 → 输出code.py
Agent X 审查 code.py → 输出审查意见
# 自己写的代码自己审——虽然不如交叉验证，但也能发现不少问题

# 方案3：人类抽检（最实际）
Orchestrator标记"需要人类确认"的关键节点
你只需要在这些节点review，而不是全程盯着
```

### 6.4 优雅降级设计

为每个关键环节准备Plan B：

| 环节 | Plan A（理想） | Plan B（降级） |
|------|--------------|--------------|
| 数据分析 | Agent深度分析+可视化 | 返回原始数据的统计摘要 |
| 内容创作 | Agent从零撰写 | 套用现有模板+填充数据 |
| 代码开发 | Agent生成完整代码 | 生成代码框架+TODO标记（你手工补） |
| 客户回复 | Agent定制个性化回复 | 使用预设的回复模板 |

**设计原则**：Plan B 产出质量低一些没关系，但不能"什么都没有"。一个80分的报告今天拿到，好过一个100分的报告三天后拿到。

### 6.5 故障复盘与系统进化

每次故障都是改进系统的机会。建立简单的故障记录：

```markdown
## 故障记录 #003
- 时间：2025-03-15 14:30
- 现象：content-writer Agent连续3次返回空结果
- 原因：输入的文章素材太长（15,000字），超过了模型的上下文窗口
- 修复：在 content-writer Skill 中增加"输入超过5000字时先由summarizer Agent压缩"
- 预防：检查所有Skill，为每个有输入的Skill设置最大输入长度限制
```

一个月后，你会发现你的多Agent系统越来越稳定——因为它从每次故障中学习了。

## 小结

多Agent编排是OPC创业者从"AI使用者"进化为"AI指挥官"的关键一步。它让你从"每次亲自跟AI对话完成一个任务"，升级到"定义目标→AI自动分解→多个AI并行执行→你只看结果"。

但请记住：**多Agent的核心不是"多"，而是"对"**。不要一上来就设计一个5层深度的Agent树。从最简单的星型结构开始：一个Orchestrator + 2-3个Leaf。把这个结构跑通、跑稳，你自然会发现哪些地方需要加更多Agent。

最成功的多Agent系统，看起来往往"平平无奇"——就几个Agent，各司其职，稳稳当当。因为真正的工程智慧不是让系统复杂，而是让复杂的东西看起来简单。
